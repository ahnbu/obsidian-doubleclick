## C. 문제

### P1. 다중 vault 포커스 버그 — 열렸는데 안 열린 것처럼 보인다

**증상**: `cowork` vault의 파일을 더블클릭했는데 화면 앞으로 나오는 건 `vibe-coding` 창이다. 사용자 눈에는 전혀 다른 노트가 보이므로 "안 열렸다"고 판단한다. 실제로는 `cowork` 창 안에서 파일이 정상적으로 열려 있고, 창만 뒤에 가려져 있다.

**원인**: `findObsidianHwnd()`가 화면에 보이는 창을 순회하다가 **제목에 `"Obsidian"`이 들어간 첫 번째 창에서 열거를 중단**한다. 어느 vault의 창인지 구분하지 않는다.

```go
// main.go:625 — 현재 코드
if strings.Contains(title, "Obsidian") {
    found = hwnd
    return 0 // 열거 중단
}
```

**재현 조건**: 옵시디언 창이 2개 이상 떠 있을 때. vault를 하나만 쓰면 발생하지 않는다.

**근거**

| 근거 | 내용 |
|---|---|
| 2026-04-11 원인분석 세션 | 실제 발생. `workspace.json`에 대상 파일이 열린 기록이 남아 있었고 handler 로그에도 URI 호출이 정상 기록됐다. 즉 "안 열림"이 아니라 "포커스 혼선"으로 결론. 문서: `20260411_01_옵시디언_md_더블클릭_원인분석_참고메모.md` |
| 실행 로그 | `2026-08-25T03:31:00Z activate-window: Obsidian 창을 찾지 못함 (3회 시도)` — 별개의 실패 사례도 존재 |
| 등록 vault 수 | 4개 (`.claude`, `cowork`, `vibe-coding`, `.agents`) — `%APPDATA%\Obsidian\obsidian.json` 실측 |

**공개 시 위험도**: 높음. vault 여러 개는 옵시디언 헤비 유저에게 흔한 구성이고, r/ObsidianMD 독자는 대부분 헤비 유저다. 재현되면 "도구가 작동하지 않는다"는 잘못된 이슈로 등록된다.

### P2. Advanced URI 플러그인 없이는 아예 작동하지 않는다

**증상**: 커뮤니티 플러그인 [Advanced URI](https://github.com/Vinzent03/obsidian-advanced-uri)를 설치·활성화하지 않은 사용자가 `.md`를 더블클릭하면 옵시디언이 주소를 못 알아듣고 실패한다.

**원인**: `buildURI()`가 **무조건** 플러그인 전용 주소를 만든다.

```go
// main.go:181 — 현재 코드
return "obsidian://adv-uri?vault=" + ... + "&openmode=true"
```

`adv-uri`는 옵시디언 기본 기능이 아니라 제3자 플러그인이 등록하는 주소다. 대체 경로가 없다.

**공개 시 위험도**: 높음. 두 가지 이유다.

1. **진입장벽** — 설치 요건이 5개(Windows · 옵시디언 · **플러그인** · 기본앱 설정 순서 · ps1 실행). 실태조사에 기록된 커뮤니티 반응 중 *"ObsidianShell은 .NET이 필요해서, 좀 더 단순한 방법이 있으면 좋겠다"*가 정확히 이 이탈 지점이다.
2. **단일 실패점** — 개인 개발자 1인이 유지하는 플러그인에 도구 전체가 종속된다. 그 플러그인이 멈추면 이 도구도 멈춘다.

**2026-03 당시엔 불가피했으나 지금은 아니다**: 최초 결정 시점에는 플러그인 없이 "이미 열린 탭으로 포커스"를 구현할 방법이 없었다. 이후 옵시디언 공식 URI가 `paneType` 파라미터를 지원하기 시작했고(1.11+), 현재 사용 중인 버전은 **1.13.7**이다.

| 플러그인 활성 목록 위치 | `<vault>/.obsidian/community-plugins.json` 읽기 | 존재. **활성화된** 플러그인 ID 배열(설치만 하고 끈 것은 제외됨) |

**이 실측이 갖는 의미**: 마지막 줄 때문에 **P2 수정은 사용자 본인 환경에서 무회귀(regression-free)다.** 4개 vault 모두 플러그인이 켜져 있으므로 지금과 완전히 동일하게 동작하고, 달라지는 건 플러그인이 없는 외부 사용자뿐이다.

### R1. vault 이름으로 창을 특정한다

**변경 내용**

1. `activateObsidian()`이 vault 이름을 인자로 받는다. `buildURI()` 시점에 이미 계산돼 있으므로 새로 구할 것이 없다.
2. `findObsidianHwnd(vaultName)`는 **2단계**로 찾는다.
   - 1단계: 제목에 `" - <vaultName> - Obsidian"`이 포함된 창 (정확 매칭)
   - 2단계: 1단계 실패 시 기존처럼 `"Obsidian"` 포함 아무 창 (하위 호환 폴백)
3. **판정 가능한 로그를 남긴다** — 매칭 단계(`exact`/`fallback`), 매칭된 창 제목, 창 핸들(HWND), `IsIconic` 여부와 복원 수행 여부, `SetForegroundWindow` 반환값을 모두 기록한다.

   현재는 `activate-window success attempt=N`만 남고 [main.go:645](../main.go:645)가 `SetForegroundWindow` 반환값을 버리기 때문에 **실제로 창이 전면에 왔는지를 로그로 알 수 없다.** 아래 검증 계획이 육안 관찰 없이 판정되려면 이 로깅이 선행되어야 하므로, R1의 필수 구성요소로 포함한다.

**왜 2단계인가**: 창 제목 형식은 옵시디언 버전·언어·설정(예: 노트 미열림 상태)에 따라 달라질 수 있다. 1단계만 두면 형식이 바뀌는 순간 포커스 기능이 통째로 죽는다. 2단계 폴백은 최악의 경우에도 **현재와 같은 수준**으로 떨어질 뿐 더 나빠지지 않는다.

**검토했으나 기각한 안**

| 안 | 기각 근거 |
|---|---|
| 창 활성화 로직 자체를 제거하고 포커스를 옵시디언에 맡긴다 | 코드는 가장 단순해지지만, 옵시디언이 최소화 상태일 때 창이 올라오지 않는 사례가 있었다. 현재 `IsIconic` → `ShowWindow(SW_RESTORE)` 처리가 그 대응이다. 기능 후퇴다 |
| 프로세스(PID) 단위로 vault를 구분한다 | 옵시디언은 vault마다 별도 프로세스라는 보장이 없다. 단일 프로세스가 여러 창을 띄우는 구성에서 틀린다 |
| 열거 중단 없이 모든 창을 모아 점수화한다 | 2단계 탐색으로 얻는 결과가 동일한데 코드만 복잡해진다 |

### R2. 플러그인이 있으면 쓰고, 없으면 공식 URI로 자동 전환한다

**변경 내용**

```
파일 더블클릭
 └─ <vault>/.obsidian/community-plugins.json 을 읽는다
      ├─ "obsidian-advanced-uri" 있음
      │    → obsidian://adv-uri?vault=<vaultName>&filepath=<relPath>&openmode=true   (현재와 동일)
      ├─ 없음
      │    → obsidian://open?vault=<vaultName>&file=<relPath>&paneType=tab
      └─ 파일을 못 읽음 / JSON 파싱 실패
           → 공식 URI (안전한 쪽으로)
```

- `<vaultName>` = `filepath.Base(vaultPath)` — 두 형식이 동일한 값을 쓴다.
- `<relPath>` = `filepath.Rel(vaultPath, filePath)`를 슬래시로 변환한 vault 루트 기준 상대경로. **확장자(`.md`)를 포함한 채로 넘긴다** — 공식 `file` 파라미터는 확장자 포함 경로를 그대로 받으므로 제거 로직을 넣지 않는다.
- 두 형식 모두 파라미터 값에 기존 `safeEscape()`를 적용한다. 파라미터 이름이 `filepath`(adv-uri) / `file`(공식)로 다른 점에 주의한다.

1. `detectAdvancedURI(vaultPath) bool` 신설 — 위 파일을 읽어 배열에 ID가 있는지 판정.
2. `buildURI()`가 판정 결과에 따라 두 형식 중 하나를 반환.
3. `obsidian-handler.config.json`에 `uriMode` 추가: `"auto"`(기본) · `"adv-uri"`(강제) · `"official"`(강제). 자동 판정이 틀렸을 때 사용자가 빠져나갈 문을 둔다.
4. 어느 모드로 결정됐는지 로그에 남긴다.

**공식 URI 폴백에서 잃는 것과 얻는 것**

| 기능 | 플러그인 있음 (adv-uri) | 플러그인 없음 (공식 URI) |
|---|---|---|
| vault 안 파일 열기 | ✅ | ✅ |
| 새 탭으로 열기 | ✅ | ✅ `paneType=tab` |
| 이미 열린 파일이면 그 탭으로 포커스 | ✅ | ❌ 탭이 하나 더 생긴다 |

**`paneType=tab`을 기본값으로 택한 근거**: 대안은 `paneType`을 아예 빼는 것인데, 그러면 **보고 있던 노트를 덮어쓴다.** 파일을 더블클릭한 사람의 기대는 "새로 열린다"이지 "보던 게 사라진다"가 아니다. 탭이 하나 더 생기는 쪽이 덜 나쁘다.

**검토했으나 기각한 안**

| 안 | 기각 근거 |
|---|---|
| 전부 공식 URI로 바꾸고 플러그인 지원을 뺀다 | "이미 열린 탭 포커스"는 이 도구를 다른 우회안과 구분짓는 핵심 기능이다. 사용자 본인의 현재 워크플로도 후퇴한다 |
| 플러그인 필수를 유지하고 README 안내만 강화한다 | 진입장벽 5개가 그대로다. 안내를 잘 써도 "뭘 또 깔라고?"에서 이탈하는 건 막지 못한다 |
| 플러그인이 없으면 자동 설치한다 | 남의 vault에 파일을 쓰는 행위다. 배포 도구가 해서는 안 되는 일이고 공개 시 즉시 비판 대상이 된다 |
| 플러그인 유무를 사용자에게 물어본다 | GUI 빌드(`-H=windowsgui`)라 대화 수단이 없다. 있어도 더블클릭마다 묻는 건 최악의 UX다 |

**엣지 케이스**

| 상황 | 처리 |
|---|---|
| `.obsidian` 폴더 경로가 커스텀으로 바뀐 vault | 파일을 못 읽음 → 공식 URI로 폴백. 동작은 하되 탭 포커스만 없음 |
| 플러그인이 설치돼 있으나 **비활성** | `community-plugins.json`은 활성 목록이므로 자동으로 "없음" 판정 → 정확 |
| vault 이름에 공백·한글·`%` 포함 | 기존 `safeEscape()` 재사용. `%` 파일명 이슈는 2026-03-18에 이미 처리됨 |
| JSON 파싱 실패 | 공식 URI로 폴백 (오류로 죽지 않는다) |

## 검증 계획

### 판정 원칙 — 육안이 아니라 로그로 판정한다

이 도구의 기능 자체가 "창을 전면으로 올리는 것"이라 **headless 검증은 원리적으로 불가능하다.** GUI가 필수인 예외에 해당하므로, 대신 두 가지로 판정 가능성을 확보한다.

1. **실행 경로를 CLI로 통일한다.** 검증은 탐색기 더블클릭이 아니라 `obsidian-handler.exe "<파일경로>"` 직접 호출로 한다. 레지스트리·탐색기 개입 변수를 제거하고, 탐색기 창이 포커스를 추가로 뺏는 것도 막는다. 레지스트리 경로 자체의 동작은 12번에서 1회만 확인한다.
2. **통과 기준을 로그 문자열로 고정한다.** 아래 표의 기준은 전부 `%TEMP%\obsidian-md-handler.log`에 남는 값이며, 사람이 화면을 보고 판정하는 항목은 12번 하나뿐이다.

**포커스 탈취 고지**: 3~7번 실행 시 옵시디언 창이 전면으로 올라온다. 병행 작업이 없는 시점에 3~7번을 묶어 연속 실행한다.

### 8번 격리 절차 — 글로벌 설정 원복 보장

`findVault()`는 [main.go:214 `loadVaults()`](../main.go:214)가 읽은 `%APPDATA%\Obsidian\obsidian.json`의 vault 목록과만 대조한다. `.obsidian` 폴더 존재만으로 vault를 인식하는 경로가 코드에 없으므로, 8번 E2E는 **테스트 vault를 글로벌 설정에 등록해야만** 성립한다. 사용자의 영구 설정을 건드리는 행위이므로 아래 절차를 반드시 지킨다.

0. **선행 확인**: `obsidian-handler.config.json`이 없거나 `uriMode`가 `"auto"`인지 확인한다. 7번의 강제 설정이 남아 있으면 이 검증은 무의미하다.
1. `%APPDATA%\Obsidian\obsidian.json`을 `<repo>/.backup/obsidian.json.<타임스탬프>`로 복사한다. **이 백업 없이 2단계로 넘어가지 않는다.**
2. 임시 vault 폴더를 만들고 옵시디언에서 열어 등록한다. **Advanced URI를 설치하지 않은 상태로 둔다.**
3. 8번 검증을 실행하고 로그를 확인한다.
4. 옵시디언에서 해당 vault를 목록에서 제거한 뒤, `obsidian.json`을 1단계 백업본과 diff한다. 차이가 있으면 백업본으로 복원한다.
5. 임시 vault 폴더는 `C:\Users\ahnbu\scripts\safe-trash.ps1`로 삭제한다.
6. **3단계에서 실패·중단되더라도 4·5단계는 반드시 수행한다.**

**8번을 생략할 수 있는 조건**: 2번(감지 로직)과 7번(공식 URI 실제 동작)이 모두 통과하면 8번은 그 둘의 결합만 확인하는 항목이다. 격리 절차 부담으로 생략할 경우 **완료 보고에 생략 사실과 근거를 명시한다.** 판정을 흐리지 않기 위해, 생략은 2·7번 통과가 확인된 뒤에만 허용한다.

### 검증 산출물 처리

### 계획 대비 설계 변경 1건 — 창 제목 매칭 규칙 확장

**계획 원안**: 창 제목에 `" - <vaultName> - Obsidian"`이 포함되면 exact 매칭.

**실행 중 발견**: 첫 실행에서 바로 폴백으로 떨어졌다.

```
04:47:49 activate-window match=fallback title="vibe-coding - Obsidian 1.13.7"
```

볼트 창이 갓 열려 **노트가 하나도 없으면 제목이 `<볼트명> - Obsidian <버전>` 형태**가 되어 선행 `" - "`가 없다. 이 상태는 드문 경우가 아니라 **핸들러가 꺼져 있던 볼트를 여는 가장 흔한 경로**다. 2회차 계획 게이트가 `참고 제안`(판정 미반영)으로 넘겼던 항목인데, 실측에서 즉시 재현됐다.

**대응**: `matchesVaultTitle()`을 신설해 두 제목 형태를 모두 처리하도록 했다.

```go
strings.Contains(title, " - "+vaultName+" - Obsidian")   // 노트 있음
|| strings.HasPrefix(title, vaultName+" - Obsidian")     // 노트 없음 (갓 연 볼트)
```

R1의 목적("vault 이름으로 창을 특정한다")을 달성하기 위한 구현 교정이며 범위 확장이 아니다. 노트 제목이 다른 볼트 이름과 같은 경우의 오매칭은 회귀 테스트(`TestMatchesVaultTitleRejectsNoteTitledLikeVault`)로 막았다.
